マルチセッション・マルチエージェント開発（複数のエージェント製品や、
エージェントと人間の協働を含む）のための資料設計フレームワーク。次の
読み手は文脈ゼロで到着する。そこで必要なのは「もっと多くの文書」では
なく、**所有権が曖昧でない文書**である: すべてのファイルが「自分は何の
正本か」を冒頭で宣言し、「いまどこにいるか」を持つファイルはちょうど
1つだけで、それ以外はいつでも安心して圧縮・削除できる — 事実の唯一の
コピーを失う恐れなしに。

以下で使うファイル名（REQUIREMENTS / ARCHITECTURE / REPORT / HANDOFF /
START_HERE / TASKS）は慣例であって必須ではない。重要なのは、管理する
全リポジトリで名前が一貫していること、そして各資料が冒頭で自分の責務を
宣言していることである。

## いつ使うか

- リポジトリの作業が複数セッションにまたがる、またはエージェント間
  （エージェントと人間の間）で引き継がれ、新しいセッションのたびに
  「再発見コスト」を払っている。
- 引き継ぎ資料が陳腐化し続けている: 日付付きスナップショットが積み
  上がり、「現在の状態」が複数ファイルに現れ、どれも信用できない。
- 既存リポジトリに新しいエージェントをオンボードするとき、全リポジトリ
  で同一のキックオフプロンプトを使いたい。
- 実装が文書より先行してしまい、事後に要件を再構成（要件の逆起こし）
  する必要がある。
- 溜まったレガシー資料を再構成する前に、目標の形と安全な移行順序が
  欲しい。

## 中核原則: 正本責務の宣言（Declared Canonical Scope）

文書の陳腐化の原因は怠慢ではなく**重複**である。同じ事実が3つの
ファイルに書かれていれば、そのうち2つを更新するのはごく普通の誠実な
仕事であり — そして3つ目のファイルが、次の読み手への罠になる。対策は
精神論ではなく構造で行う:

1. **すべての資料は冒頭に正本責務の宣言を置く**: この資料が何の単一の
   正本（single source of truth）であり、隣接する事実はどの資料の持ち物
   か。同梱の雛形（本スキルと同じ場所の `templates/en/`・`templates/ja/`
   配下）はすべて、最初の節としてこの宣言欄を確保している。
2. **1つの事実に所有者は1人。** その事実が必要な他の資料は、書き写す
   のではなく所有者へのリンクを置く。
3. **実状態は文書に優先する。** 食い違ったときはリポジトリの観測結果
   （git log・PR の状態・動くコード・CI 結果）が一次情報であり、直す
   べきは文書の側である — と宣言自体に書いておく。
4. **正本の本文は、エージェントが実際に読むファイルに置く。** 実測例:
   gitignore されたエージェント固有の設定ファイルに書かれた規約は、
   同じリポジトリで作業する別のエージェント製品からは見えなかった。
   両方のエージェントが読み込むコミット対象の規約ファイル（例:
   `AGENTS.md`）に正本を昇格させ、エージェント固有ファイルは薄い
   ポインタに落とすことで、ドリフトを根本から解消した。

このスキルの残り — 4分割・キックオフファイル・living handoff・台帳 —
はすべて、プロジェクトが蓄積する4種類の事実（意図・設計・経緯・現在地）
にこの原則を適用したものである。

## 4分割型（The Four-Document Split）

| 資料 | 単一の正本として持つもの | 更新タイミング |
| --- | --- | --- |
| REQUIREMENTS | 満たすべきこと: 機能・非機能要件、非スコープ、受け入れ基準とその状態 | スコープの決定時、受け入れ基準の状態が（証跡つきで）変わったとき |
| ARCHITECTURE | 現行の as-built 設計: コンポーネント、データフロー、不変条件、key files | マージ済みの変更が構造や不変条件を変えたとき |
| REPORT | 経緯: 調査、行き止まり、実測記録、決定の背景 | 作業単位が残す価値のある知見を生んだとき、他資料が経緯を手放すとき |
| HANDOFF | 現在地と次の一手 | 常時。作業の区切りごとに圧縮 |

### REQUIREMENTS — 意図の資料

機能要件、非機能要件、明示的な非スコープ、そして全基準が検証方法と
状態（証跡つきの `done` か `not yet`）を持つ受け入れ基準表。

実測に基づくポイント2つ:

- **実装完了後でも要件の逆起こしはやる価値がある。** コードが既にある
  のに要件定義書を書くのは逆順に感じられるが、そこで生まれる受け入れ
  基準表が「残作業の正本」になる — どのセッションの記憶にも依存せず、
  何が証明済みで何がそうでないかを次のエージェントに正確に伝える。
- **日付と数値は記憶からではなく、成果物から読み直して書く。** 実測例:
  逆起こしした要件定義書に書かれたフェーズ完了日が、`git log` の実際の
  日付と1日ずれていた。敵対的レビューが捕捉した。以来、正本資料に書く
  日付・数値は必ずリポジトリから読み直すのが規則になった。

### ARCHITECTURE — as-built の資料

いま存在している設計 — 理想の設計ではなく、ここに至る道のりでもない
（それは REPORT の仕事）。コンポーネント、データフロー、不変条件、
ストレージの形、key files の地図。

**意味論と不変条件を書き、コードが既に所有している「形」を書き写さ
ない。** 型定義を丸写しした仕様書は最初の1週間でドリフトする。代わりに
こう宣言する:「フィールドの形は `<型定義ファイル>` が正本。本資料は
各フィールドの意味と、どの組み合わせが合法かを説明する」。

### REPORT — 経緯の資料

調査メモ、行き止まり、ベンチマーク・実測記録、決定の背景。追記中心・
時系列。

REPORT の存在こそが、フレームワーク全体を安全にする: **他のどの資料も
恐れなく圧縮できるのは、経緯が「削除」ではなく「ここへの移動」だから**
である。HANDOFF が古い仮説を手放すとき、REQUIREMENTS が過去の検討を
落とすとき、残す価値のある部分はまず REPORT に着地する。「なぜこう
作られているのか」への答えは、エージェントが毎セッション読む資料を
散らかすことなく、ここに残る。

### HANDOFF — 生きている「いま」の資料

現在地と次の一手だけ。規律が厳格なので、後述の独立した章で扱う。

### 分割のスケーリング

小さなリポジトリでは、REPORT は git 履歴+PR 本文で代替でき、
ARCHITECTURE は README 内の1節でもよい — ファイルは畳んでよいが、宣言
は残す（「経緯は PR 本文にある。README のこの節が as-built の正本」）。
大きなリポジトリでは、同じ責務規則のもとで資料をトピック別に分割して
よい。スケールしても消えないのは「正本責務の宣言」の方である。

## START_HERE: 標準キックオフファイル

管理する全リポジトリに、同じ名前で1枚。新規参加のエージェントが最初に
読み、正本の所在と着手方法を知る。内容は順に:

1. **このリポジトリは何か** — 1〜2行。数ヶ月変わらないもの。
2. **読み順** — 正本資料の番号付きリスト（典型的には README →
   REQUIREMENTS → ARCHITECTURE → HANDOFF → TASKS）。
3. **検証コマンド** — PR 前に必ず通すコマンド（build・test・lint・
   スキャナ）。または、それらを正本として持つ資料の節を1つだけ指す。
4. **主要ゲート** — 承認なしに越えない境界（本番デプロイ、外部発信、
   有料 API、公開操作）。検証コマンドと同様、本文をここに置くのは他に
   所有する資料がない場合だけ。規約資料（例: `AGENTS.md`）が所有する
   場合はこの節をポインタにする — 所有権は移動するのであって共有しない。
5. **次の一手へのポインタ** — HANDOFF の「次の一手」節への参照。
   次の一手そのものは書かない。

START_HERE を生かし続ける唯一の規則: **時点情報を書かない。** この
ファイルは「真実がどこにあるか」を書き、「いま何が真実か」は書かない。
そう書かれていれば数ヶ月ノーメンテで生き続ける — 入口ファイルに必要な
のはまさにそれである。

見返りはフリート全体に及ぶ: 約30リポジトリへこのファイルを標準配備した
結果、完全に同一のキックオフプロンプト（「START_HERE.md を読んで、
handoff から続行」）がどのリポジトリでも機能するようになった —
リポジトリごとのプロンプト調整が消えた（field-tested）。

命名: 汎用には `START_HERE.md`。規約の異なる複数のエージェント製品が
同居するリポジトリでは、エージェント名を冠した変種（ファイル名に
エージェント名を前置する）も成立する — ただし「読者ごとに入口は
1リポジトリ1枚」を守ること。

このファイルのフリート横断配備は「配備タスク」である。完了条件は配備
ループ自身の記録ではなく、全対象の存在スキャン実測（後述の「検証」を
参照）。

## Living Handoff の規律

1リポジトリに HANDOFF は1枚、持つのは現在だけ。規律:

- **サイズ予算: 目安1,000トークン以下。** それを超えると、次の
  エージェントの読解コストと陳腐化リスクが価値より速く成長する。
- **保持するのは**: 現在のゴールと成功指標・key files・直近の決定
  （各1行）・実行済みコマンド・既知の問題・Do-not-re-read リスト・
  次の一手、のみ。
- **「触る前に知るべき罠」を最上位に置く** — 知らなければ次の
  エージェントが1時間を失う1〜2個の事実（資料の本文を固定している
  テストスイート、古く見えて現役のディレクトリ、二度実行してはいけない
  コマンド）。
- **リズムで圧縮する**: 長い作業では数ターンごと、作業の区切りごと、
  そして最終報告やコンテキスト移行の前に必ず。古い仮説・行き止まり・
  長いログ・重複記述を削る — 残す価値のあるものを所有者の資料（通常は
  REPORT）へ移してから。
- **Do-not-re-read リストを維持する。** 資料を削除・置換したら、何を
  消したか・残す内容はどこへ行ったか・git 履歴から復元可能であることを
  記録する。この習慣1つが削除を安全で安価にする — 次のエージェントは
  陳腐化ファイルを再読もしないし、失われたのかと探しもしない。
- **secret 禁止。** credential・token・credential 入りログ・実データを
  handoff に置かない — ここは今後の全セッションが必ず読む場所である。

こうして保たれた handoff は「現在形のスナップショット」になる。対案の
追記型 handoff（セッションごとに追記が積もる形式）は、数週間で「現在の
状態」を経緯の下から発掘しなければ読めなくなることが実測されている
（アンチパターン参照）。

## タスク台帳（The Task Ledger）

台帳ファイル（例: `TASKS.md`）1枚が作業キューの正本: 進行中・ブロック
中・完了のタスクを表で持つ — ID・タスク・優先度・状態・備考。

- **行を委譲 spec として書く。** 指摘型の行には file:line の位置・
  最小の修正案・confidence（確度）を書く。そう書かれた行は自己完結した
  作業指示になる: サブエージェント（あるいは別のエージェント製品）が
  追加の文脈なしに実行できる。実測結果: 台帳の行だけを spec として
  14体の実装エージェントへ並列委譲したところ、全員がテスト緑の変更を
  返し、空振り（no-op）はゼロだった。
- **検証ログの方針を台帳ヘッダに宣言する**: 残すのは直近の検証実行
  のみ。過去の実行はこのファイルの git 履歴にある。宣言がないと、誠実
  なエージェントほど毎回追記する — あるリポジトリでは3週間で追記が
  30行を超え、タスクが埋もれた（アンチパターン参照）。
- **履歴は期間ごとに1行**、詳細は git log と PR 本文に任せる。台帳が
  記録するのは「その期間に何が出て、どの PR か」だけ。物語らない。
- **REQUIREMENTS との分担**: 受け入れ基準表は「要件は満たされたか」を
  要件レベルで答える。台帳は「次の作業単位は何か」を運用レベルで答える
  （レビュー指摘や雑務を含む）。要件の完了は受け入れ行に証跡が付いた
  とき — 台帳のタスクにチェックが付いただけでは完了ではない。

## アンチパターン

1. **日付付きハンドオフ資料の積み重ね。** セッションごとの
   `HANDOFF_<日付>.md` は勤勉に見えて逆である: 各スナップショットは
   翌日には陳腐化し、山は単調に育ち、次のエージェントは1つの現在地を
   再構成するために N 本の資料を読まされる。living HANDOFF 1枚+経緯は
   REPORT、でこの山全体を置き換える。
2. **検証ログの全量追記。** 検証実行のたびに台帳や handoff へ追記
   すると、数週間でシグナルがノイズになる（実測: 3週間で30行超）。
   直近の実行だけを残し、「過去は git 履歴」とヘッダに宣言する。
3. **未マージの作業を前提にした「完了」記述。** feature ブランチ上で
   書かれた「X は完了」は、default ブランチから読まれた瞬間 — あるいは
   そのブランチが死んだ瞬間 — に虚偽になる。実測例: ある資料統合で、
   前提だった feature が結局マージされず、6箇所の完了主張を巻き戻す
   ことになった。正本資料に書く時点事実は、執筆時点の default ブランチ
   に対して全数チェックする — 抜き取りではなく。
4. **エージェントが読まないファイルに規約の正本を置く。** gitignore
   された・エージェントから見えないファイルに置かれた規約は、次の
   エージェントにとって存在しないのと同じ。全エージェントが読み込む
   コミット対象ファイルに正本を置き、エージェント固有ファイルは薄い
   ポインタにする。
5. **現在地の三重管理。** ブリーフと handoff と台帳がそれぞれ「いま
   どこか」を持つと、それぞれ独立に腐り、数日で食い違う（同じ完了履歴
   を3資料で更新していたリポジトリの監査で観測）。現在地の所有者は
   ちょうど1人: HANDOFF。他はすべてポインタ。

## 検証（Verification）

状態についての文書が信頼を得る方法は実測だけである。規則は3つ:

- **未検証項目をチェックリストとして書けば、それがそのまま作業指示に
  なる。** REQUIREMENTS（または専用の検証節）に明示的な「未検証」
  リストを保ち、各項目に「何を実行・観測すれば検証できるか」を書く。
  次のエージェントへの指示は文字どおり「未検証リストを消し込め」で
  済む — 別途のタスク起こしが不要になる（field-tested）。
- **配備・伝播タスクの完了条件は、ループ自身の記録ではなく全対象
  スキャン。** 変更を多数の対象へ展開するとき（全リポジトリへの
  ファイル配備、全資料のヘッダ更新）、完了の証跡は最後に行う全対象
  横断スキャン1回 — ヒット数を期待総数と突き合わせる。実測の教訓:
  「全リポジトリへ配備済み」と報告された作業が、後の全数スキャンで
  30対象中6対象の未配備を検出した。ループが中断・再開された際に計画の
  一部が静かに脱落していた。対象ごとの記録では捕まえられないものを、
  スキャンは捕まえる。
- **主張はローカル checkout ではなく、リポジトリの実状態に対して検証
  する。** ローカル checkout は思った以上の頻度で古いブランチに
  乗っている。まず fetch し、「次の読み手にとって何が真実か」を確認
  するときは `origin/<default>` からファイルを読む。

## 移行: 既存資料の再構成

積年の資料があるリポジトリへの導入は、それ自体が危険なタスクである。
実測で確立した順序:

1. **棚卸しと分類**: 全資料を「正本候補 / 陳腐化 / 重複 / 歴史資料」に
   分類する。
2. **動かす前に、テストと CI を grep する**。資料のパスや本文を固定
   する doc-contract テスト（資料に特定フレーズが含まれることや、パス
   の実在を assert するテスト）はエージェント管理のリポジトリでは
   一般的で、一見きれいな再構成が普通に壊す。何が固定されているかが、
   そもそも何を動かせるかを決める。
3. **消される側の資料にしか存在しない事実を監査する** — 未決事項・
   警告・未完タスク・安全上の注意 — そして先に正本資料へ移す。削除が
   安全になるのはこのパスの後だけ。
4. **経緯を REPORT へ畳み、旧ファイルを削除する。** git 履歴が保全
   する。各削除は HANDOFF の Do-not-re-read リストに復元可能性の注記
   つきで記録する。リポジトリの方針として歴史資料を working tree に
   残す必要がある場合は、削除の代わりに「索引 README（各ファイルが
   何だったか・なぜアーカイブしたか）つきのアーカイブディレクトリ」を
   使う。
5. **参照切れをスキャンする — バッククォートで書かれたパス言及も
   含めて。** Markdown リンクチェッカーが検証するのはリンクであって、
   インラインコードで言及されたパスではない。実測の教訓: ある再構成は
   リポジトリのリンクガードを通過したが、移動済みファイルへの
   バッククォート付きパス参照が3件壊れたままだった。旧パスの全文
   grep だけがそれを捕捉した。
6. **時点事実を default ブランチに対して全数再検証する**
   （アンチパターン3）— 再構成の完了宣言はその後で。

## スコープ外

- SDLC の工程分類やステージゲート — このスキルが構造化するのは資料で
  あって、その周りのプロセスではない。
- UI 仕様書・デザイン文書。
- ツール固有の設定（エージェント設定ファイル・CI 設定・権限設定）。
  フレームワークは「どのエージェント製品が読むか」に対して意図的に
  中立である。

## 出自（Provenance）

このスキルは、主にコーディングエージェントが複数製品で保守する約30
リポジトリのフリート運用 — セッション引き継ぎが毎日発生し、資料設計の
失敗が最終的に必ず「無駄になった1セッション」として表面化する環境 —
から蒸留された。上記のすべての規則は、観測された失敗か検証された復旧に
